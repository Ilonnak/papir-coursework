# Структура та функції вебзастосунку «папір.»

## 1. Призначення

Вебзастосунок призначений для перегляду канцелярських товарів, керування товарними пропозиціями та оформлення замовлень.

Основний процес:

1. Адміністратор готує товарні пропозиції.
2. Покупець обирає товари та додає їх до кошика.
3. Покупець оформлює замовлення.
4. Адміністратор приймає замовлення в обробку.
5. Під час видачі фіксується оплата.
6. Замовлення отримує статус «Виконане».

Передбачено самовивіз із навчального пункту видачі та оплату при отриманні. Застосунок фіксує факт оплати, але не виконує банківські платежі.

## 2. Архітектура

Застосунок складається з трьох основних частин:

| Частина | Технології | Відповідальність |
|---|---|---|
| Клієнт | Vue 3, Vue Router, Pinia, Vite | Відображення сторінок, введення даних, надсилання запитів і показ результатів |
| Сервер | C#, ASP.NET Core Web API | Автентифікація, перевірка прав, валідація, бізнес-правила та робота з даними |
| База даних | PostgreSQL | Збереження користувачів, каталогу, кошиків і замовлень |

Сервер працює з PostgreSQL через Entity Framework Core та Npgsql.

Клієнт звертається до серверного API через HTTP. У локальному режимі Vite пересилає запити `/api`, `/uploads` та `/images` до сервера.

Конфігурація цього пересилання знаходиться у `frontend/vite.config.js`.

## 3. Користувачі та доступ

| Користувач | Доступні можливості |
|---|---|
| Гість | Перегляд каталогу й товарів, пошук, фільтрація, сортування, реєстрація та вхід |
| Покупець | Можливості гостя, власний кошик, оформлення та перегляд власних замовлень |
| Адміністратор | Керування товарами, категоріями, видимістю, зображеннями та замовленнями покупців |

Гість – неавтентифікований відвідувач, а не окремий зареєстрований обліковий запис.

Обмеження інтерфейсу доповнюються серверними перевірками. Приховування адміністративних посилань саме по собі не є механізмом захисту API.

| Маршрут | Сторінка | Призначення |
|---|---|---|

Позначення `:id` означає ідентифікатор конкретного товару.

## 8. Автентифікація та розмежування доступу

Реєстрацію, перевірку облікових даних і формування JWT виконує `AuthService`.

Паролі зберігаються у вигляді хешів із використанням `PasswordHasher<User>`.

Клієнт передає токен у заголовку:

```text
Authorization: Bearer <token>
```

Сервер перевіряє підпис, строк дії та параметри токена. Адміністративні операції потребують відповідних прав.

Публічна реєстрація створює покупця й не призначена для отримання адміністративних повноважень.

Покупець працює лише зі своїми кошиком і замовленнями. Належність даних перевіряється на сервері.

## 9. Каталог і конфігуратор пропозицій

Каталог відображає доступні для публічного перегляду товари.

Адміністративне керування дозволяє налаштовувати:

- назву та категорію;
- опис і характеристики;
- ціну;
- залишок;
- зображення;
- видимість у каталозі.

У межах реалізації конфігуратор пропозицій є адміністративним керуванням цими параметрами. Окремий підбір сумісних опцій покупцем не реалізовано.

Для товару зберігається версія запису. Якщо адміністратор намагається зберегти застарілі дані після зміни товару, сервер відхиляє конфліктне оновлення.

Непорожня категорія захищена від видалення, яке спричинило б втрату її товарів.

## 10. Кошик та оформлення замовлення

Кошик зберігається в PostgreSQL і пов’язаний із користувачем.

Оформлення виконує метод `CreateOrderAsync` у `OrderService.cs`.

Основні етапи:

1. Перевірка контактних даних і параметрів запиту.
2. Початок транзакції та узгодження операцій користувача.
3. Перевірка повторного запиту за ключем ідемпотентності.
4. Отримання позицій кошика.
5. Блокування й перевірка відповідних товарів.
6. Перевірка актуального складу кошика, кількостей і цін.
7. Створення замовлення та його позицій.
8. Зменшення залишків.
9. Очищення кошика.
10. Збереження результатів і підтвердження транзакції.

У позиції замовлення зберігаються назва товару та ціна на момент оформлення. Подальше редагування поточної назви або ціни не повинно змінювати ці історичні відомості.

Якщо операція завершується помилкою до підтвердження транзакції, виконані в її межах зміни відкочуються.

## 11. Повторні запити та конкурентні зміни

Оформлення використовує `IdempotencyKey`, щоб повторне надсилання того самого запиту не створювало ще одне замовлення.

Разом із ключем зберігається відбиток параметрів запиту. Повторне використання ключа з іншими параметрами відхиляється.

Для узгодження одночасних операцій застосовуються:

- транзакції;
- блокування записів через `FOR UPDATE`;
- перевірка версії товару;
- перевірка підтвердженого складу кошика.

Ці механізми спрямовані на запобігання повторному списанню, продажу понад доступний залишок і перезапису актуальних даних застарілою формою.

## 12. Статуси, оплата та скасування

| Поточний статус | Дозволена дія |
|---|---|
| «Нове» | Прийняти в обробку або скасувати неоплачене замовлення |
| «В обробці» | Завершити після оплати або скасувати неоплачене замовлення |
| «Виконане» | Подальші переходи не передбачені |
| «Скасоване» | Подальші переходи не передбачені |

Фіксація оплати доступна після прийняття замовлення в обробку.

Завершення потребує зафіксованої оплати або її явного підтвердження під час видачі.

При скасуванні неоплаченого замовлення його товари повертаються до залишків у межах транзакції. Повторне повернення залишків не допускається.

Скасування оплаченого замовлення та повернення коштів у реалізованому обсязі не передбачені.

## 13. Зображення товарів

Завантаження зображень виконує `ImageStorageService`.

Перед збереженням перевіряються:

- наявність непорожнього файлу;
- розмір до 5 МБ;
- дозволений тип;
- сигнатура растрового формату.

Підтримуються JPEG, PNG, WEBP і GIF.

Файл отримує сформоване сервером ім’я та зберігається в:

`backend/wwwroot/uploads/products`

У даних товару зберігається відносний шлях до зображення. Зображення передаються клієнту сервером.

## 14. Обробка помилок

Сервіси повертають результати операцій через `ServiceResult`.

Відповіді API містять повідомлення про результат або причину відмови. Залежно від ситуації також передаються код помилки та додаткові дані.

Основні статуси відмов:

| HTTP-статус | Приклад |
|---|---|
| `400` | Некоректні вхідні дані |
| `401` | Відсутня або недійсна автентифікація |
| `403` | Недостатньо прав або немає доступу до чужих даних |
| `404` | Запитаний ресурс не знайдено |
| `409` | Конфлікт залишку, версії товару, стану замовлення або повторного запиту |
| `500` | Необроблена внутрішня помилка |

Клієнтський модуль `api.js` перетворює відповіді сервера на повідомлення для інтерфейсу.

## 15. Тестування

Інтеграційні тести знаходяться в:

`backend.tests/CourseworkIntegrationTests.cs`

Вони перевіряють, зокрема:

- доступ гостя й адміністратора;
- реєстрацію та вхід;
- ізоляцію кошиків і замовлень покупців;
- перевірку цін, кількостей і залишків;
- пошук, фільтрацію та сортування;
- оформлення й повторне надсилання запитів;
- оплату та переходи статусів;
- конкурентні операції;
- відкат транзакції;
- збереження ручних змін при повторному наповненні.

Тести працюють з окремою PostgreSQL-базою `coursework_web_automated_tests`.

Команда запуску з папки `Project`:

```powershell
dotnet test .\backend.tests\Backend.Tests.csproj --logger "console;verbosity=normal"
```

Збережений результат від 08.11.2026 наведено у `test-results.txt`: 16 успішних тестів. Цей журнал не замінює результат нового запуску.
