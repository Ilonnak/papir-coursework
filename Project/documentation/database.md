# Створення та оновлення бази даних

## 1. Використаний підхід

Застосунок «папір.» використовує PostgreSQL для збереження користувачів, товарів, кошиків і замовлень.

Доступ до даних реалізовано через Entity Framework Core та Npgsql. Створення й оновлення структури бази виконуються SQL-скриптами.

Стандартні міграції Entity Framework Core у проєкті не використовуються. Команду `dotnet ef database update` виконувати не потрібно.

Підготовкою схеми керує клас `DatabaseInitializer`, розташований у файлі:

`backend/Services/DatabaseInitializer.cs`

Його виклик під час запуску налаштований у:

`backend/Program.cs`

## 2. SQL-скрипти

Скрипти знаходяться в папці `backend/Database` та виконуються в такому порядку:

| Файл | Призначення |
|---|---|
| `000_full_schema_for_empty_db.sql` | Створює базові таблиці та зв’язки в порожній базі |
| `001_extend_existing_schema.sql` | Додає або перевіряє поля, індекси й обмеження, потрібні застосунку |
| `002_concurrency_and_idempotency.sql` | Доповнює схему полями контролю версій, ідемпотентності та ідентифікації демонстраційних товарів |

Перший скрипт створює сім основних таблиць:

- `users` – користувачі;
- `categories` – категорії товарів;
- `products` – товари;
- `cart_items` – позиції кошиків;
- `orders` – замовлення;
- `order_items` – позиції замовлень;
- `order_statuses` – довідник статусів.

Скрипт `001` забезпечує, зокрема:

- додаткові відомості про товари;
- контакти отримувача замовлення;
- спосіб отримання й оплати;
- ознаку та час оплати;
- збереження назви товару в позиції замовлення;
- перевірки допустимих цін, залишків і кількостей;
- унікальність email без урахування регістру;
- обмеження видалення категорії, яка містить товари.

Скрипт `002` забезпечує наявність:

- `products.version` – версії товару для виявлення застарілих змін;
- `products.seed_key` – незмінного ключа демонстраційного товару;
- `orders.idempotency_payload_hash` – відбитка параметрів запиту для перевірки повторного оформлення.

Частина полів уже присутня у скрипті `000`. Наступні скрипти також підтримують доповнення бази, створеної попередньою версією схеми.

## 3. Порядок підготовки схеми

Метод `InitializeSchemaAndStatusesAsync`:

1. Виконує скрипт `000`.
2. Виконує скрипт `001`.
3. Виконує скрипт `002`.
4. Перевіряє наявність основних статусів замовлень і додає відсутні.

Використовуються статуси:

- «Нове»;
- «В обробці»;
- «Виконане»;
- «Скасоване».

Підготовка схеми не є очищенням бази. Скрипти містять перевірки наявності об’єктів і розраховані на повторне виконання в межах підтримуваної структури.

Для обліку виконаних оновлень використовується службова таблиця `schema_migrations`. Скрипти `001` і `002` записують у неї ідентифікатор оновлення та час його першого успішного застосування.

Ініціалізатор не використовує цю таблицю для пропуску раніше виконаних скриптів: під час запуску вони виконуються повторно з перевірками наявності об’єктів. Автоматичні команди відкату не реалізовані.

Наявність несумісної структури або даних, що порушують нові обмеження, може спричинити помилку виконання.

## 4. Налаштування підключення

Усі команди нижче виконуються в PowerShell із папки `Project`, де знаходяться `backend`, `frontend` і `start.ps1`.

Перед першим запуском створюється робоча конфігурація:

```powershell
Copy-Item .\backend\appsettings.example.json .\backend\appsettings.json
```

Якщо робочий файл уже існує та налаштований, повторно замінювати його шаблоном не потрібно.

У `ConnectionStrings:DefaultConnection` зазначаються власні параметри PostgreSQL:

```text
Host=localhost;Port=5432;Database=coursework_web;Username=postgres;Password=<YOUR_POSTGRES_PASSWORD>
```

Заповнювач пароля потрібно замінити фактичним значенням.

Також у конфігурації заповнюються:

- `Jwt:Key` – ключ підпису токенів;
- паролі адміністратора й покупців у розділі `DemoSeed`.

Робочий файл конфігурації з паролями та ключем до комплекту передавання не включається.

## 5. Створення бази

Саму базу PostgreSQL потрібно створити до запуску серверного ініціалізатора.

У pgAdmin можна скористатися командою `Create → Database` або виконати в Query Tool для бази `postgres`:

```sql
CREATE DATABASE coursework_web;
```

Назва створеної бази повинна збігатися з параметром `Database` у рядку підключення.

Таблиці вручну створювати не потрібно. Користувач PostgreSQL має володіти правами, необхідними для створення та зміни об’єктів у цій базі.

## 6. Створення схеми й демонстраційних даних

Відновлення залежностей сервера:

```powershell
dotnet restore .\backend\Backend.csproj
```

Підготовка схеми та демонстраційне наповнення:

```powershell
dotnet run --project .\backend\Backend.csproj -- --seed-demo --seed-only
```

Значення параметрів:

- `--seed-demo` – явно запускає демонстраційне наповнення;
- `--seed-only` – завершує програму після підготовки даних без запуску HTTP-сервера.

Після успішного наповнення виводиться повідомлення:

```text
Демонстраційні дані каталогу «папір.» успішно перевірено та підготовлено.
```

Повернення до запрошення PowerShell після цієї команди є очікуваним результатом.

Команда `dotnet restore` лише відновлює залежності та не додає товари до бази.

## 7. Демонстраційне наповнення

Демонстраційні дані створює метод `SeedDemoDataIfDevelopmentAsync`.

Для явного наповнення потрібно використовувати параметр `--seed-demo`, щоб не залежати від середовища запуску.

Початковий набір містить:

- 6 категорій;
- 23 товари, серед яких є прихований товар і товар без залишку;
- адміністратора;
- двох покупців;
- приклади замовлень, якщо таблиця замовлень порожня.

Без фільтрів у публічному каталозі стандартного набору відображаються 22 товари, оскільки один товар прихований.

Дані стандартного каталогу визначені в `DatabaseInitializer.cs`. Зображення включені до `backend/wwwroot`, а їхні відносні шляхи записуються в дані товарів.

Повторне наповнення:

- не перезаписує наявні демонстраційні товари, знайдені за `SeedKey`;
- зберігає ручні зміни таких товарів;
- не змінює паролі вже створених користувачів;
- не відновлює базу до початкового стану.

Для відтворення стандартного каталогу на іншому комп’ютері копія робочої бази автора не потрібна.

## 9. Перевірка створених даних

У Query Tool, підключеному саме до бази застосунку, можна виконати:

```sql
SELECT COUNT(*) AS users_count FROM users;
SELECT COUNT(*) AS categories_count FROM categories;
SELECT COUNT(*) AS products_count FROM products;
SELECT COUNT(*) AS orders_count FROM orders;
```

Перевірка товарів і посилань на зображення:

```sql
SELECT id, name, price, stock_quantity, is_active, image_path
FROM products
ORDER BY id;
```

Якщо таблиці створені, але товарів немає, потрібно перевірити результат команди з `--seed-demo --seed-only`.

Якщо дані в базі є, але каталог порожній, перевіряються:

- параметри підключення запущеного сервера;
- пошук і фільтри в інтерфейсі;
- видимість товарів;
- відсутність іншої запущеної копії проєкту на тих самих портах.

## 10. Оновлення наявної бази

Перед змінами схеми бази з потрібними даними слід створити резервну копію.

Для наявної бази:

1. Перевірити рядок підключення.
2. Переконатися, що використовується потрібна копія проєкту.
3. Запустити сервер – підготовка схеми виконується перед прийманням запитів.
4. Перевірити журнал на наявність помилок.

Якщо потрібно також перевірити або додати демонстраційне наповнення, використовується команда з `--seed-demo --seed-only`.

Автоматичний відкат SQL-скриптів не реалізований. Відновлення попереднього стану потребує резервної копії або окремо підготовлених і перевірених SQL-команд.

## 11. Тестова база

Інтеграційні тести використовують окрему базу:

`coursework_web_automated_tests`

Вона перестворюється тестовим набором і не повинна містити потрібні робочі дані.

Для виконання тестів користувач PostgreSQL повинен мати права на створення й видалення тестової бази.

Команда запуску з папки `Project`:

```powershell
dotnet test .\backend.tests\Backend.Tests.csproj --logger "console;verbosity=normal"
```

Тестову базу не потрібно вказувати як робочу базу застосунку.
